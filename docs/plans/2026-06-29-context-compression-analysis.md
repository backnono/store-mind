# 上下文压缩方案对比分析与技术选型

## 问题定义

当前 `store-mind` 的对话上下文管理存在三个交织的问题：

1. **天花板问题**：`ListRecentMessages(sessionID, 40)` 硬编码 40 条上限，用户持续对话必然超出
2. **聚焦问题**：即使未爆窗，历史消息量增大会稀释 LLM 注意力，回答质量随轮次增加而下降
3. **语义 bug**：当前 SQL 为 `ORDER BY id ASC LIMIT 40`，取的是最旧的 40 条而非最近 40 条，对话越长丢的信息越关键

以下基于市面上 5 款产品（Manus、Claude Code、OpenClaw、Cursor、LangChain）的上下文工程实践，结合 `store-mind` 的产品特性做交叉分析。

---

## 产品特性定位

在分析各方案前，先明确 `store-mind` 与参考产品的关键差异：

| 维度 | Manus / Claude Code / Cursor | Store Mind |
|------|------------------------------|------------|
| **产品类型** | 代码 Agent / 通用任务 Agent | 知识库问答 Agent |
| **核心交互** | 单次复杂任务（多步工具链） | 多轮连续对话（追问、切换话题） |
| **主要 token 消耗** | 工具调用结果（shell 输出、文件内容） | 对话历史、上下文实体信息 |
| **工具调用频率** | 高（50+ 次/任务），单次输出大 | 低（检索、筛选为主），单次输出小 |
| **上下文关键信息** | 任务进度、文件路径、错误堆栈 | 用户偏好、已确认实体、对话意图链 |
| **已有基础设施** | — | ContextStack（轮次摘要）、DecayCheck（衰减检测） |

**核心差异一句话**：代码 Agent 的上下文压力主要来自**工具调用的横向膨胀**，而 Store Mind 的压力主要来自**对话轮次的纵向累积**。

## 各家方案横向对比

### 一、方案矩阵

| 维度 | Manus | Claude Code | OpenClaw | Cursor | LangChain |
|------|-------|-------------|----------|--------|-----------|
| **核心理念** | 三板斧：Reduce / Offload / Isolate | 三层防线：清除 → 压缩 → 子Agent | 可插拔 ContextEngine | 少放东西（按需加载） | Agent 自主判断压缩时机 |
| **压缩触发** | 固定阈值 | 固定阈值（窗口快满时） | 固定阈值（180K 时触发） | 不压缩（源头控制） | Agent 自主决策 |
| **压缩粒度** | 两阶段：Compact → Summarize | 一轮压缩（结构化摘要） | 分段摘要再合并 | — | 自主选择段落 |
| **可恢复性** | 强（文件引用 + URL） | 中（保留文件引用） | 中（占位符替换） | 强（文件系统） | 弱 |
| **工具结果处理** | Compact 版切换 | Tool Result Clearing | head+tail 截断 | 写文件 + grep/tail | 未特别强调 |
| **子 Agent** | 三层架构（隔离上下文） | 按需拆分 | 未强调 | 不依赖 | 未强调 |
| **KV Cache 优化** | 系统级重视（工具定义不变） | 隐含 | 未强调 | 未强调 | 未强调 |
| **量产参数** | 不公开 | 不公开 | **公开**（30% 单结果上限、1.2x 安全边距、保留 3 轮） | 46.9% token 降低 | 未公开 |

### 二、各方案与 Store Mind 的适配度

#### Manus（Reduce + Offload + Isolate）

**精华可取之处**：
- **结构化摘要（Schema 约束）**：不让模型自由发挥，用预定义模板约束摘要格式。这对 Store Mind 的 ContextStack 天然适配——你的 `ContextStackItem` 已经有 `Intent`、`ResolvedEntities`、`SystemAction`、`SystemSummary` 字段，本质上就是一个 schema 约束的摘要结构
- **可恢复压缩**：信息不在视野但可找回。对知识库问答场景，这意味着用户说「刚才那个粉底液」时，Agent 能从 ContextStack 中找回已推荐的产品 ID

**不适合之处**：
- **Offload（文件系统）**：代码 Agent 的文件系统是天然外脑，但 QA Agent 没有频繁的文件读写场景，这个维度几乎用不上
- **Isolate（多 Agent）**：当前阶段为上下文隔离引入子 Agent 架构，ROI 极低。你的对话复杂度远不到需要拆分上下文的程度
- **Compact 两阶段**：Manus 的 Compact 阶段主要针对工具结果，你的工具调用量小，不需要这一层

> **适配度：★★★☆☆** — 结构化摘要思路高度可借鉴，Offload 和 Isolate 过重

#### Claude Code（三层防线）

**精华可取之处**：
- **优先级递进**：能用轻量手段解决就不上重量级——这个哲学应该直接作为 Store Mind 的实施原则
- **Tool Result Clearing**：对 QA Agent 也适用：工具调用返回的检索结果、产品详情，在当前轮次消化后就可以标记为可清除
- **结构化摘要保留任务进度**：摘要中包含「已做决策 + 原因 + 未解决问题」——QA 场景中就是「已确认偏好 + 已推荐产品 + 待确认问题」

**不适合之处**：
- **子 Agent**：同上，过早引入
- **摘要粒度**：Claude Code 按「任务」维度做摘要，QA 需要按「话题 / 意图链」维度

> **适配度：★★★★☆** — 三层防线哲学 + 结构化摘要可直接复用

#### OpenClaw（参数化工程）

**精华可取之处**：
- **公开的工程参数**直接可用：
  - 单条工具结果 ≤ 30% 上下文窗口
  - Token 估算 × 1.2 安全边距
  - 保留最近 3 轮完整对话不压缩
  - 窗口剩余 20K token 时必须触发摘要
- **head+tail 截断**：保留输出首尾、省略中间。QA 场景中产品描述、检索结果都适用
- **分段摘要 + Fallback**：大消息跳过不阻塞流程——这在 QA 中处理超长知识库返回时很有用
- **强制保留 opaque identifiers**：摘要中不丢失产品 ID、SKU——这是 QA 场景的硬需求

**不适合之处**：
- ContextEngine 可插拔接口设计对当前阶段偏重
- 部分参数（如 180K 触发阈值）针对代码 Agent 调优，QA 场景需要重新标定

> **适配度：★★★★★** — 工程参数和截断策略可直接落地，是目前最务实的选择

#### Cursor（Dynamic Context Discovery）

**精华可取之处**：
- **按需加载**：不把不需要的东西放进上下文。对 QA 场景：不要一次性把所有检索结果都塞进 prompt，让 Agent 按需请求
- **写文件 + grep/tail**：大输出不直接进上下文。QA 中知识库检索返回 10 个产品时，只放摘要列表，详情按需加载
- **A/B 结果很有说服力**：token 减少 46.9% 且表现提升

**不适合之处**：
- 核心思路是「入口控制」而非「存量压缩」，它解决不了对话历史累积的问题
- 按需加载在 QA 中主要体现在工具调用侧，对历史消息不适用

> **适配度：★★★☆☆** — 入口控制思路可用于优化检索结果注入，但不能替代对话压缩

#### LangChain（自主压缩）

**精华可取之处**：
- **Agent 自主判断压缩时机**比固定阈值更智能：
  - 刚完成子任务时（中间状态已转化为结论）
  - 提取完结论后（原始数据不再需要）
  - 准备消费大量新信息前（提前腾空间）
- 这正好对应 QA 场景：用户说「好的，再看看别的」意味着前一个话题可以压缩

**不适合之处**：
- 自主决策对模型推理能力要求高，当前阶段稳定性和可预测性不如固定规则
- 作为远期方向很好，但不适合 MVP

> **适配度：★★★☆☆** — 方向正确但过早，适合 V2/V3 迭代

## 综合推荐：Store Mind 的上下文压缩方案

### 推荐原则

沿用 Claude Code 的哲学：**能用轻量手段解决就不上重量级**。结合 Store Mind 的低工具调用、高对话轮次的特性，建议分三阶段推进：

### 第一阶段（立即修复）

**目标**：止血，让对话不会因消息数硬上限而崩溃

| 步骤 | 内容 | 参考来源 |
|------|------|---------|
| 修复 SQL 语义 | `ORDER BY id ASC LIMIT 40` → `ORDER BY id DESC LIMIT 40` 后反转 | — |
| Token 计数器 | 接入 tiktoken（Python sidecar 已有）或 Go 侧的简单估算（char/2 ≈ token） | OpenClaw 1.2x 安全边距 |
| Token 感知滑动窗口 | 替换硬编码 40 为 `min(40, max_messages_before_threshold)`，按 token 上限动态截断最近 N 条 | 通用方案 |

### 第二阶段（核心能力）

**目标**：上线摘要缓冲，让对话可以「无限」延续

```
┌────────────────────────────────────────────────────────┐
│                    LLM Context Window                   │
│                                                        │
│  ┌──────────┐  ┌───────────────────────────────────┐  │
│  │  System  │  │  Context Memory (压缩摘要区)       │  │
│  │  Prompt  │  │                                    │  │
│  └──────────┘  │  [T1] 用户在找油皮适用的粉底液      │  │
│                │       → 已推荐产品 A(¥280)、B(¥320) │  │
│                │       → 用户认为 A 太干、偏好滋润型  │  │
│                │  [T2] 用户询问了持妆效果            │  │
│                │       → B 持妆 8h、已确认            │  │
│                │  [T3] 用户转而询问口红推荐           │  │
│                │       → 偏好滋润质地、预算 200       │  │
│                └───────────────────────────────────┘  │
│                                                        │
│  ┌─────────────────────────────────────────────────┐  │
│  │  Recent Messages (最近 3 轮完整保留)             │  │
│  │                                                  │  │
│  │  User: 之前说的那个口红有什么色号？               │  │
│  │  Assistant: 您之前关注的口红是 Y 品牌...         │  │
│  └─────────────────────────────────────────────────┘  │
└────────────────────────────────────────────────────────┘
```

**具体设计**：

| 设计点 | 方案 | 理由 |
|--------|------|------|
| **触发机制** | 阈值触发 + 衰减触发双轨 | 阈值兜底安全、衰减利用对话间隙 |
| **摘要 Schema** | 复用 `ContextStackItem` 结构（Intent + ResolvedEntities + SystemAction + SystemSummary） | 已有定义，零成本接入；结构化约束保证摘要质量稳定（参考 Manus） |
| **压缩粒度** | 压缩「已关闭话题」的完整轮次，保留最近 3 轮不压缩 | OpenClaw 参数可直接套用 |
| **可恢复性** | 摘要中强制保留产品 ID / SKU，原始消息不删除 | 参考 OpenClaw 的 opaque identifiers 强制保留规则 |
| **保留策略** | 摘要保留：意图 + 已确认偏好 + 已推荐实体；丢弃：寒暄、已解决的子问题、中间 tool_call 过程 | — |
| **单轮阈值** | 单条消息 > 30% 窗口时做截断（head+tail） | 直接引用 OpenClaw 参数 |

**融合已有基础设施**：

```
已有 DecayCheck           → 触发摘要的时机之一（用户离开 >30s 时触发 LightSummary）
已有 ContextStackItem     → 摘要的存储结构（每条摘要一个 item）
已有 AppendContextStack()  → 滑动窗口保留最近 N 轮摘要
已有 BuildTurnSummary()   → 构建单轮摘要的工厂函数
```

### 第三阶段（远期优化）

| 方向 | 内容 | 触发条件 |
|------|------|---------|
| **自主压缩** | Agent 判断压缩时机（参考 LangChain） | 摘要缓冲跑稳后，A/B 测试自主触发 vs 固定规则 |
| **话题切换感知** | 检测到用户切换话题时，自动压缩前一个话题 | 需要意图识别支持「话题切换」信号 |
| **检索结果按需加载** | 知识库检索先返回摘要列表，Agent 按需请求详情（参考 Cursor） | 单次检索结果 > 5000 token 时启用 |

## 各方案优缺点总结

| 方案 | 核心优势 | 核心弱点 | 对 Store Mind 的价值 |
|------|---------|---------|---------------------|
| **Manus** | 结构化摘要 + 可恢复压缩 + 文件系统外脑 | Offload / Isolate 链路重，对 QA 场景过设计 | 结构化摘要思路直接复用 ContextStack |
| **Claude Code** | 三层防线优先级清晰，渐进式压缩 | 面向代码 Agent 优化，QA 话题维度欠缺 | **三层防线哲学** 作为实施原则 |
| **OpenClaw** | **工程参数公开**、head+tail 截断、分段摘要 + Fallback | 接口设计偏重 | **直接落地的参数和策略** |
| **Cursor** | 源头控制（少放东西），A/B 验证 46.9% 降低 | 不解决对话历史累积问题 | 检索结果注入优化，辅助手段 |
| **LangChain** | 自主压缩时机智能，方向正确 | 成熟度不足、对模型要求高 | V2/V3 方向 |
| **纯滑动窗口** | 实现简单 | 丢失早期关键信息，无压缩 | 仅适合短暂对话 |
| **摘要缓冲** | 平衡信息密度和窗口大小，行业主流 | 摘要有信息损失，需要调优 prompt | **推荐作为核心方案** |
| **向量检索式** | 无限上下文 | 碎片化、相关性不完美，基础设施重 | 暂不推荐（话题跳跃不频繁） |
| **递归摘要** | 适合超长对话 | 实现复杂、延迟累积 | 暂不推荐（对话长度不到这个量级） |

## 关键工程参数参考（OpenClaw）

| 参数 | 值 | 适用场景 |
|------|-----|---------|
| 单工具结果上限 | ≤ 上下文窗口 30% | 检索结果、产品详情 |
| Token 安全边距 | × 1.2 | 中文字符需要补偿（中文字符 ≈ 1.5–2 token） |
| 保留原始轮次 | 最近 3 轮 | 保持对话连贯性 |
| 触发摘要阈值 | 窗口剩余 ≤ 20K token | 给下一轮留足空间 |
| 摘要强制保留 | 产品 ID、SKU、UUID | QA 场景硬需求 |
